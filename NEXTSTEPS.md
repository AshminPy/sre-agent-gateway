## 2. (Item #1) Redesign the RCA output: eliminate 3x root-cause duplication, adopt an executive-first evidence-backed template

**Effort estimate:** Small-to-medium. Core fix (steps 1-5: eliminate the 3x duplication) is a genuinely small, mechanical change — one new prompt field, one function-signature change, one truncation-length fix — touching prompts.py, rca_builder.py, and ~15 lines of main.py. The full recommended scope (reordering, Trigger field, Markdown conversion, owner tags) adds moderate but still low-risk work across the same two files, plus a re-run of the eval harness to confirm the new LLM fields are populated reliably. No infra/IAM/Terraform changes required — pure application-code change in agent/.

### Current state

FACT (read agent/main.py lines 76-320, 493-508; agent/prompts.py lines 213-224; invoke_agent.py lines 260-370):

The `investigate()` function returns THREE overlapping representations of the same finding: `summary` (raw LLM dict), `executive_summary` (prose string), and `rca_report` (full text report). The root-cause sentence appears three times, traceable exactly:
1. Line 502: `"executive_summary": _build_executive_summary(summary, inv, ctx)` — builds a paragraph from `summary.get("likely_root_cause")`, truncated to 500 chars.
2. Line 231, inside `_build_rca_report()`: `L.extend(wrap(_build_executive_summary(summary, inv, ctx), ...))` — the SAME function called a second time with the SAME inputs, embedded verbatim as report section "1. EXECUTIVE SUMMARY". Byte-identical to (1).
3. Lines 128-133 + 236-241: report section "2. ROOT CAUSE ANALYSIS" → "Primary Cause:" renders `str(root_cause)[:400]`, where `root_cause` is pulled from the exact same `summary.get("likely_root_cause")` field — just sliced to 400 chars instead of 500. Same sentence, third appearance.

Root schema cause: agent/prompts.py RCA_BUILDER_USER (lines 213-224) gives the LLM only ONE root-cause field (`likely_root_cause`, max 200 chars). There is no separate short-headline vs long-detail field, so main.py has to slice the same string two different ways to fake two granularities — that slicing IS the duplication bug.

Format: `_build_rca_report()` (lines 103-320) renders with manual box-drawing (`SEP = "━"*64`) and a hand-rolled 60-char word-wrapper (`wrap()`, lines 200-210) — plain-text/terminal-only, not Markdown. Section order today: 1 Executive Summary, 2 Root Cause Analysis, 3 Impact Assessment, 4 Remediation, 5 Investigation Metadata. Impact is currently a weak placeholder ("Service Status: DEGRADED — verify active pod count", line 270) and sits after root cause, not before it.

Confirmed first-party downstream confusion: invoke_agent.py (lines 260-263, 308-313, 354-359) branches on `"rca_report" in result` vs `elif "executive_summary" in result` as mutually-exclusive alternatives — the CLI test harness itself doesn't know which field is authoritative, direct evidence the current shape causes ambiguity even for the one consumer that exists today.

The repo already has an established, higher-quality convention for human-facing RCA docs: RCA_REPORT.md (18KB, checked structure) uses numbered sections (1. Executive Summary, 2. Timeline, 3. Errors Observed, 4-5. Root Cause #1/#2, 6-8 transparency/caveat sections, 9-11 audit/verification/lessons) with NO repeated content across sections — proof the team already knows how to avoid this pattern when writing by hand; the code-generated report has regressed from that bar. The user's own global rca-writer skill (~/.claude/skills/rca-writer/SKILL.md) independently specifies: timeline, impact, root cause (with evidence), contributing factors, what went well/wrong, corrective actions with owners, related runbooks/ADRs — and explicitly requires "owner TBD" on every corrective action, which the current REMEDIATION section (prevention_measures, main.py 295-299) does not include.

### Recommended approach

Keep the 3-part JSON shape (`summary` raw dict, `executive_summary` short string, `rca_report` full text) but make each one genuinely different content instead of the same sentence at 3 truncation lengths. Add one new LLM-produced field, `root_cause_headline` (≤150 chars), to the RCA_BUILDER JSON schema in prompts.py, and keep `likely_root_cause` as the longer, evidence-cited detail (used only in the Root Cause Analysis section). `executive_summary` and section "1. Summary" both use `root_cause_headline`; section "3. Root Cause Analysis" uses the full `likely_root_cause` plus evidence/contributing factors — genuinely different text, not re-truncation. Reorder sections to executive-first: Summary → Impact → Root Cause Analysis (with Trigger) → Remediation → Investigation Metadata, matching Google SRE Workbook and PagerDuty convention of surfacing impact/status before the detailed technical narrative. Switch the rendered format from hand-rolled box-drawing/60-char-wrap to Markdown (`##` headings, bullets, bold) so the same string works as a terminal report, a Jira/PagerDuty ticket body, and a Slack message without a second format to maintain. This is a minimal, code-mapped change — same function shapes, same call sites, different literal content per section and one new optional LLM field with a safe fallback.

### Key decisions

- Add `root_cause_headline` (≤150 chars) as a new field in the RCA_BUILDER LLM schema, separate from the existing `likely_root_cause` (≤200-400 chars) — this is what actually kills the duplication, since main.py currently has no second field to draw from and instead re-slices one string three ways.
- Compute `_build_executive_summary()` exactly ONCE per request and pass the resulting string into `_build_rca_report()` as a parameter, instead of `_build_rca_report()` calling it a second time internally (main.py line 231) — removes duplication call #2 with a one-line signature change.
- Reorder report sections to Summary → Impact → Root Cause Analysis → Remediation → Investigation Metadata (impact before detailed root cause), matching Google SRE Workbook and PagerDuty convention, instead of today's Summary → Root Cause → Impact → Remediation → Metadata.
- Add a `trigger` field (what specifically activated the fault, distinct from root cause = why the system was vulnerable) as an optional LLM output, defaulting to "Not established from available evidence" when absent — never fabricate, matches the user's troubleshooting.md rule against inventing values.

GATEWAY EGRESS/CONTENT VISIBILITY — iac/agent/agent_gateway.tf wires only an IAP REQUEST_AUTHZ extension+policy (google_network_services_authz_extension.iap, google_network_security_authz_policy.iap). Grep across iac/ found no Model Armor CONTENT_AUTHZ extension/policy actually attached to the gateway. model_armor.tf's two templates exist but are only consumed by agent-code-level sanitize calls (agent/main.py:542-596), and agent_engine.tf:72-78 gates the MODEL_ARMOR_TEMPLATE env var to `enable_agent_gateway ? {} : {...}` — i.e. app-level Model Armor only runs when the gateway is OFF. The repo's own commit history (iac/agent/.claude/state/*.json) documents this as a deliberate 2026-07-17 fix: Model Armor CONTENT_AUTHZ at the gateway does TLS MITM, which broke the agent's mutual-TLS Vertex endpoint (the cert-verify RCA in FINAL_RCA.md/ADR-002); IAP REQUEST_AUTHZ (header/attribute-based, no payload inspection) replaced it to match the official codelab. Net effect: there is currently no gateway-level Model Armor content-inspection signal to build dashboards around — this corrects the framing that the gateway is "doing Model Armor content inspection" today; it is not, by design.

GKE-SIDE — iac/gke-access/gke.tf creates an Autopilot cluster with container/compute/logging/monitoring APIs enabled. GKE Autopilot cannot disable Cloud Logging/Monitoring (system logs, mandatory audit logs, workload logs, control-plane metrics all flow automatically), but nothing in this repo tags those GKE-side logs with the agent's run_id for correlation.

### Recommended approach

Extend the existing Cloud Trace + structured-logging foundation rather than introducing a new observability stack — this repo has already built 70% of the plumbing (otel.py, per-run JSON logs, 7 log-based metrics, gateway Log Analytics). Close five concrete gaps: (1) standardize on OpenTelemetry GenAI semantic-convention attributes (gen_ai.*) across ALL spans — not just gemini_client.py's LLM spans — so Agent Engine's native Tools/Models/Usage tabs render tool-call data automatically; (2) add a dedicated child span per MCP tool call with gen_ai.tool.name/mcp.method.name and propagate a W3C traceparent header to GKE Remote MCP so Google's own remote-MCP tracing correlates server-side; (3) stamp logging.googleapis.com/trace + spanId onto every structured log event (sre_agent_run, tool_failures) so Cloud Trace and Cloud Logging become click-correlated; (4) add a Terraform-managed google_monitoring_dashboard for the signals the native tabs don't cover (MCP source split, gateway authz denial rate, cost trend) since none exists today; (5) correct the mental model that the gateway does Model Armor content inspection — it currently does not (by deliberate, evidence-backed design), so gateway-level "content visibility" work should target the agent-code sanitize path instead, or be treated as a separate, harder decision to re-open the MITM tradeoff. None of this requires new infrastructure categories — it's instrumentation depth on files that already exist.

### Key decisions

- Decide whether to propagate W3C traceparent headers to the GKE Remote MCP endpoint (mcp_client.py) — recommended yes, since it's a low-effort header addition that unlocks Google's own server-side MCP trace spans; note the endpoint is Preview/Pre-GA so validate empirically rather than assuming full parity with GA-documented behavior.
- Decide whether Model Armor CONTENT_AUTHZ should ever be reinstated at the gateway. This is NOT an observability-only decision — it reopens the exact TLS MITM / certificate-verify failure the 2026-07-17 RCA resolved. Recommend treating gateway content-inspection visibility as out of scope until/unless that security tradeoff is separately revisited; build observability around the agent-code Model Armor path (agent/main.py _sanitize) instead, which currently only fail-open-logs transport errors, not actual filter-match verdicts.

CONCRETE GAPS / HARDCODED ASSUMPTIONS FOUND (with evidence):

1. This is a real drift risk between the "edit GCS directly" workflow the code advertises and the "IaC is source of truth" workflow the rest of the repo follows — not yet empirically tested against a live `terraform plan` (flagging as HYPOTHESIS, not confirmed by execution).

2. Same-project 2nd cluster isn't supported by iac/gke-access at all: `google_container_cluster.sre_test` is a single `count = var.create_gke_cluster ? 1 : 0` resource (gke.tf:53), not a `for_each` over a list of cluster definitions.

3. New Project C (a genuinely new GCP project hosting cluster #2/#3) requires a second, manually copy-pasted apply of the whole iac/gke-access stack (new backend prefix + new `project_b_id`/`gke_cluster_name` vars) — the stack takes single scalar variables, not a list/for_each over target projects (variables.tf:10-13, 35-39). This is moderate, arguably acceptable friction (a new project is a legitimate new blast-radius/state boundary), but it is manual, undocumented as a repeatable pattern, and not something a 3rd project owner could self-serve without reading the Terraform.

4. MCP_REGISTRY (agent/mcp_client.py:97-113) hardcodes exactly two source keys, `gke_remote_mcp` and `k8s_mcp`, and multiple functions branch on those two literal names rather than iterating the registry generically:
   - `get_tools_for_source()` (lines 497-558): hand-written `if mcp_source == "gke_remote_mcp": return (...)` / else returns a different literal string — not registry-driven.
   - `get_registry_prompt()` (lines 561-585): a SEPARATE hardcoded text block naming only these two sources. Verified via repo-wide grep — this function is dead code, defined but called nowhere in the repo. It is exactly the kind of "config sprawl" the task asked me to look for: a whole duplicate description of the tool-source registry that a maintainer must remember to update (or delete) when adding source #3, and today isn't even wired up.
   - `_map_to_custom_tool()` (lines 289-299): a fixed 6-pair dict hardcoding a `gke_remote_mcp → k8s_mcp` fallback mapping specifically — no generalized N-source fallback chain.
   - `call_tool()` (lines 302-368) itself is a binary `if is_gke_remote: ... else: ...` dispatch, including a GKE-specific arg-builder (`_build_gke_args`, lines 221-286, hand-written per tool name for the GKE Remote wire schema: `parent`/`resourceType`/etc.) versus the custom-MCP branch which just passes `dict(arguments)` straight through. There is no per-source "adapter" abstraction to plug a 3rd, differently-shaped source (e.g., a non-Kubernetes source like a PagerDuty/Datadog read-only MCP) into — you'd grow this central function's branching further.

5. The "which MCP source to use" decision is independently computed in THREE places and two of them are redundant, hardcoded copies of the same binary rule:
   - `_build_cluster_registry()` sets `mcp_primary`/`mcp_fallback` per cluster via `"gke_remote_mcp" if cluster_type == "gke" else "k8s_mcp"` (mcp_client.py:152-153).
   - `context_resolver.py` reads that already-resolved value into `resolved_context["primary_mcp_source"]` (line 52, 72-73) — this is the correct, single-source-of-truth read.
   - `mcp_router.py` Phase 1 (lines 82-88) IGNORES `resolved_context["primary_mcp_source"]` entirely and re-derives `selected_mcp` from raw `cluster_type` via its own identical hardcoded ternary. Verified via grep: `primary_mcp_source` is never referenced in mcp_router.py. Adding a 3rd `cluster_type` value or a 3rd MCP source therefore requires editing the ternary in two places that must be kept in sync by hand, with nothing enforcing that they agree — the clearest concrete evidence of structural duplication in this codebase.

6. The custom Cloud Run MCP fallback server itself (mcp/server.py) is single-cluster BY CONSTRUCTION, independent of the agent's own registry: `get_k8s_clients()` is `@lru_cache(maxsize=1)` and reads one `GKE_CLUSTER_ENDPOINT`/`GKE_CA_CERT_GCS_PATH` pair from env (lines 34-46); `iac/agent/cloudrun_mcp.tf` sets a single scalar `PROJECT_ID = var.project_b_id` (line 54-57). So even though the agent's `clusters.json` registry can in principle hold N clusters, any cluster that needs the custom-MCP fallback (e.g., a non-GKE/on-prem cluster where GKE Remote MCP doesn't apply) cannot share this one Cloud Run deployment — a 2nd such cluster needs an entirely separate Cloud Run service (new SA, new IAM, new Terraform resource), not a registry edit.

### Recommended approach

Don't rewrite the architecture — the cluster-registry half (GCS-backed clusters.json with runtime reload) is already a good, working pluggable design and should be left alone. The concrete work is narrower: (a) make the Terraform-managed bootstrap of clusters.json list-driven instead of single-entry so it stops silently colliding with the "edit GCS directly" workflow the code already advertises; (b) collapse the MCP-source-selection ternary that exists in two places (mcp_client.py and mcp_router.py) down to one, by making mcp_router.py consume `resolved_context["primary_mcp_source"]` that context_resolver.py already computes; (c) turn MCP_REGISTRY from "a dict two functions branch on by name" into "a dict whose entries carry their own tool-list, tool-docs, and arg-builder," so a 3rd source is one new entry, not four edited functions; (d) delete the dead `get_registry_prompt()` function rather than let it silently drift out of sync with the real registry; (e) leave the new-Project-C-copy-the-stack workflow as-is for now (YAGNI — extract to a Terraform module only when a real 3rd project shows up) and leave the single-cluster custom-MCP-server limitation as a documented constraint rather than a build-it-now item, since GKE Remote MCP already covers the common multi-project GKE case and the custom MCP is explicitly a fallback.

- Should MCP_REGISTRY become a true plugin registry (each entry owns its arg-builder/tool-docs/fallback pointer) now, or only when a 3rd source is actually requested — recommend doing it now since it's a contained, low-risk refactor and the duplicated ternary is an active correctness risk (two places can disagree), not just a hypothetical scaling concern.

### Best practices & references

- GKE Fleet Management lets clusters from multiple projects register into one logical, centrally-managed group without redeploying consumers — validates the repo's existing GCS-backed clusters.json approach as the right shape of pattern (a live, externally-editable registry decoupled from redeploy), even though it's a lighter hand-rolled version rather than the full Fleet API. ([source](https://www.digitalapplied.com/blog/mcp-server-patterns-enterprise-ai-agents))

([source](https://arxiv.org/pdf/2405.10467))
- Classic Adapter design pattern (GoF): wrap each incompatible external interface behind a common interface so the caller (here, call_tool()/mcp_router.py) depends only on the common shape, not on each source's quirks — the textbook justification for turning the current per-source if/elif branches into per-registry-entry adapter callables. ([source](https://en.wikipedia.org/wiki/Adapter_pattern))

## 6. (Item #7) RCA accuracy eval suite: golden dataset + LLM-judge scoring + confidence-calibration checks

**Effort estimate:** Medium (roughly 1-2 focused days). Most of the hard infrastructure already exists (trajectory scoring, Vertex AI Experiments wiring, GCS upload, k8s fixtures) — the real work is dataset consolidation (mechanical), authoring 8 missing golden cases with expected_component fields (needs domain judgment per scenario), adding one new PointwiseMetric plus a calibration-report function (small, additive code), and wiring one new GitHub Actions manual/nightly workflow.

### Current state

Evaluation already exists in three separate, overlapping, un-unified places, none of which do semantic root-cause grading, and none of which are wired into CI: (1) eval/dataset.jsonl — all 16 invoke_agent.py scenarios with a free-text 'reference' ground truth, scored by eval.py using a crude heuristic (split reference on punctuation, count words >4 chars that literal-match in the response — eval.py:87-113); (2) agent/eval/golden_cases.py — only 8 of the 16 scenarios (missing rollout, liveness, highrestart, job, cronjob, 3tier, progress, unreachable), each with expected_trajectory (ordered tool names), expected_keywords (literal substrings), expected_confidence_min, scored by agent/eval/run_eval.py via trajectory_precision/recall/in_order_match plus keyword_accuracy (literal substring count, run_eval.py:64-105); (3) eval_native.py, which calls the newer unified `vertexai.Client().evals.create_evaluation_run()` (Agent Platform GenAI Client path) with Google's built-in AutoRater metrics question_answering_quality and groundedness — the only path that uses an LLM judge at all, but it grades general answer quality/groundedness, not 'did the agent name the correct root cause.' agent/eval/run_eval.py separately also supports submitting trajectory metrics to the older `vertexai.preview.evaluation.EvalTask` (trajectory_precision, trajectory_recall, trajectory_in_order_match, trajectory_any_order_match — run_eval.py:174-243). All 16 scenarios have reproducible, declarative k8s fixtures (k8s/*.yaml for test-incidents scenarios, k8s/demo/*.yaml for demo-incidents scenarios), so the ground-truth root causes are grounded in real, re-creatable cluster state, not synthetic text. Nothing in .github/workflows/*.yml or the Makefile runs any of the three eval scripts; the only CI-adjacent check is scripts/smoke_test.sh, which greps the response for the literal string 'rca_report' / 'RCA REPORT' — it proves the agent responded, not that the root cause is correct. The agent's own output already carries a confidence_band (auto/review/escalate, agent/state.py, agent/nodes/rca_builder.py) and per-run token/cost telemetry (agent/otel.py, event_type=sre_agent_run in Cloud Logging) — both are unused by any of the three eval scripts today, so there is no calibration check (is 'AUTO' band actually right more often than 'REVIEW'?) and no cost-per-correct-RCA tracking.

### Recommended approach

Do not build a fourth eval script — consolidate. Merge the three fragmented sources (eval/dataset.jsonl's 16 references, golden_cases.py's 8 trajectory/keyword cases, invoke_agent.py's 16 SCENARIOS payloads) into one golden_dataset.jsonl with 16 complete entries, each carrying: the request payload, expected_trajectory, an atomic 'expected_root_cause' fact plus 'expected_component' (the specific resource that is actually at fault, e.g. order-db not order-api, postgres-db not web-frontend — this is the field the current keyword scorer cannot check and is exactly where a cascading-failure agent could hallucinate the wrong culprit while still keyword-matching 'OOMKilled'), expected_confidence_band (not just a min score — use it for calibration), and expected_fix_keywords. Keep trajectory scoring exactly as-is (trajectory_precision/recall/in_order_match are legitimate, deterministic, free — Google's own agent-evaluation metrics use the identical definitions). Replace literal keyword-matching for root-cause correctness with a Vertex AI PointwiseMetric LLM-judge rubric (0/1/2 scale: 0 = wrong or fabricated cause, 1 = right symptom/component but wrong or incomplete causal chain, 2 = correct root cause AND correct at-fault component) scored against the golden reference, run through vertexai.evaluation.EvalTask alongside the trajectory metrics already in run_eval.py — this is additive to existing code, not a rewrite. Add a calibration report step (plain Python, no Vertex dependency) that buckets all 16 results by the agent's own confidence_band and reports root-cause-correct rate per bucket; a red flag is 'AUTO' band scoring less than ~90% correct, because AUTO means the agent is telling operators no human review is needed. Run the full 16-scenario suite as a manual/nightly GitHub Actions job (not on every PR) because it requires live GKE cluster state and costs real Gemini judge-call money; gate merges only on a lightweight subset (the 3 'simple' scenarios) if a pre-merge signal is wanted.

### Key decisions

- Root-cause scoring method: use LLM-judge PointwiseMetric with a 3-point rubric (0/1/2), not exact string match and not pure keyword overlap — keyword matching provably passes on cascading/3tier scenarios even when the agent blames the wrong tier, because 'OOMKilled' appears in both the correct and incorrect explanations.
- Single source of truth for the golden dataset: consolidate eval/dataset.jsonl + agent/eval/golden_cases.py + invoke_agent.py SCENARIOS into one file (e.g. eval/golden_dataset.jsonl) covering all 16 scenarios with the union of fields each currently has; delete or thin the duplicates so nobody edits one and silently desyncs the other two.
- Add an explicit 'expected_component' / at-fault-resource field per scenario, separate from 'expected_root_cause' text — needed so the judge (and any keyword fallback) can specifically check attribution, not just symptom recognition.
- Confidence-band calibration is graded as its own metric, separate from root-cause correctness — a run can have a correct root cause AND a miscalibrated (over-confident or under-confident) band; both are reportable failures.
- Cadence: full LLM-judge suite runs nightly/on-demand against the live Agent Engine, not per-PR — live k8s fixtures + judge-model calls cost money and take minutes per scenario (eval.py already sleeps 0.5s/scenario for quota); a cheap 3-scenario trajectory-only subset can run in CI per-PR if a merge gate is wanted.
- Judge model version must be pinned and recorded per eval run (in the results JSON already written by eval.py/run_eval.py) so that a later Gemini model upgrade doesn't silently shift historical pass rates — treat this the same way the repo already treats reasoning-engine versioning.

### Best practices & references

- Vertex AI Gen AI evaluation service (agent evaluation) defines the standard dataset schema (prompt, reference_trajectory, predicted_trajectory, response, reference) and the four built-in trajectory metrics: trajectory_exact_match, trajectory_in_order_match, trajectory_any_order_match, trajectory_precision/recall — agent/eval/run_eval.py already implements these correctly against this exact spec. ([source](https://cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/evaluate))
- Custom LLM-judge metrics are defined via PointwiseMetric + PointwiseMetricPromptTemplate with `criteria`, `rating_rubric` (a dict mapping score strings to descriptions), and `input_variables` (which dataset columns the judge sees, e.g. prompt + reference + response) — this is the exact mechanism to add root-cause-correctness grading without inventing custom infrastructure. ([source](https://cloud.google.com/vertex-ai/generative-ai/docs/models/eval-python-sdk/determine-eval))
- EvalTask.evaluate() returns both eval_result.summary_metrics (aggregate) and eval_result.metrics_table (per-instance) — run_eval.py's run_vertex_eval() already reads summary_metrics/metrics_table, so adding the new PointwiseMetric to its existing `metrics=[...]` list is a small diff, not new plumbing. ([source](https://googlecloudplatform.github.io/applied-ai-engineering-samples/genai-on-vertex-ai/gemini/evals_playbook/notebooks/1_gemini_evals_playbook_evaluate/))
- Google's Agent Platform also exposes a separate GenAI-Client evaluation path (`vertexai.Client().evals.create_evaluation_run()`) with built-in AutoRater metrics like question_answering_quality and groundedness — eval_native.py already uses this; it complements but does not replace a root-cause-specific rubric, since it grades general answer quality, not causal-attribution correctness. ([source](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/evaluation-agents))
- Golden-dataset practice: validate any LLM-judge against human-labeled examples before trusting it at scale (aim for 75-90% judge/human agreement), and build the rubric from real observed failure modes rather than generic criteria — here that means writing the 0/1/2 rubric anchors using the specific wrong-attribution failure mode already identifiable in the cascading/3tier scenarios. ([source](https://www.comet.com/site/blog/llm-as-a-judge/))
- Minimum viable golden datasets are cited at 50-100 examples to catch obvious failures; this repo's 16 scenarios are below that bar for statistical confidence in a pass-rate number, so treat the 16-case suite as a regression/smoke gate (did this specific known failure mode come back?) rather than a statistically powered accuracy benchmark, and grow it over time from real production RCA disagreements. ([source](https://www.getmaxim.ai/articles/building-a-golden-dataset-for-ai-evaluation-a-step-by-step-guide/))

### Risks & gotchas

- Live-cluster dependency: golden_cases.py's run_local() and any remote run require sre-test-cluster to actually have the k8s/*.yaml and k8s/demo/*.yaml fixtures applied and in the expected broken state at eval time — a fixture that self-healed or was manually kubectl-fixed will silently produce a false 'agent got it wrong' result. - `agent/otel.py` already tags spans with `sre.source_type`, so a PagerDuty-originated run is automatically distinguishable in traces/logs with zero extra code.
- The **Agent Gateway** (`iac/agent/agent_gateway.tf`, `google_network_services_agent_gateway.sre_egress`) is `google_managed { governed_access_path = "AGENT_TO_ANYWHERE" }` — confirmed by its own comments and `docs/architecture.md` ("governs all of the agent's egress"). It governs the agent's OUTBOUND calls (model, MCP, telemetry), not inbound query calls. **A PagerDuty-triggered invocation does not touch the gateway at all** — it is a separate, direct call to the Reasoning Engine's `:query` endpoint, authorized purely by project/resource-level IAM.
- `iac/agent/iam.tf` already has a working least-privilege pattern to copy: per-component dedicated service accounts (`mcp_runtime` in `cloudrun_mcp.tf`), resource-scoped bindings (`google_cloud_run_v2_service_iam_member`), and a `runtime_project_roles` list with justifications in `docs/least-privilege-iam.md`.
- `iac/agent/cloudrun_mcp.tf` is the existing template for "add a Cloud Run service to this stack": dedicated Artifact Registry repo, dedicated runtime SA, `google_cloud_run_v2_service` gated behind a feature-flag variable (`enable_custom_mcp`), placeholder image so `terraform apply` succeeds before the real image is built.
- `iac/agent/monitoring.tf` has 7 log-based metrics + 2 alert policies + 1 email notification channel already wired — the pattern to extend for webhook-specific metrics (e.g., signature failures).
- `iac/agent/apis.tf` gates API enablement on feature flags (`core_apis` vs `gateway_apis`) — `pubsub.googleapis.com` and `secretmanager.googleapis.com` are NOT currently enabled anywhere in this stack.
- The agent's real investigation latency is FACT from this repo's own `TROUBLESHOOTING_LOG.md`: full runs logged at **56–62 seconds** (line 76: "Agent response [62.0s]", line 734: "[56-59s]"). This matters directly for the webhook architecture (see below).

### Recommended approach

Do NOT call the Reasoning Engine synchronously from the PagerDuty webhook request. PagerDuty requires a 2xx response within 5 seconds for generic/V3 webhooks (verified: PagerDuty/developer-docs `docs/webhooks/02-Behavior.md`, "Timeouts" section) but this agent's own investigations run 56-62s (measured in this repo's TROUBLESHOOTING_LOG.md) and can loop longer. Trying to hold the HTTP connection open, or doing the work in a goroutine/thread after returning 202, is also unsafe on Cloud Run: without "CPU always allocated" billing, Cloud Run throttles a container's CPU to near-zero the instant the HTTP response is flushed, so background work after `return` is unreliable. The correct shape is two small decoupled Cloud Run services connected by Pub/Sub, mirroring the existing `cloudrun_mcp.tf` pattern:

1. PagerDuty side: a V3 Webhook Subscription (`incident.triggered`, filtered to the relevant service/team) delivers to a public Cloud Run "receiver". Manage this subscription with Terraform (official `PagerDuty/pagerduty` provider, `pagerduty_webhook_subscription` resource) rather than a manual console click, consistent with this repo's "IaC before manual" rule — gated behind a new `enable_pagerduty_integration` flag, same convention as `enable_custom_mcp`/`enable_agent_gateway`.
2. Receiver (Cloud Run v2, `ingress = "INGRESS_TRAFFIC_ALL"`, unauthenticated `roles/run.invoker` for `allUsers` since PagerDuty cannot present a GCP-signed identity): read the RAW request body, verify `X-PagerDuty-Signature` (HMAC-SHA256 over the raw body, `v1=` prefix, comma-separated for secret rotation, constant-time compare) against a secret pulled from Secret Manager, de-dup on the `X-Webhook-Id` header, then publish a small normalized message to a Pub/Sub topic and return 202 — all well inside the 5s budget.
3. Pub/Sub push subscription (OIDC-authenticated) invokes a second, internal-only Cloud Run "worker" (`INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER`, same ingress setting already used for `cloudrun_mcp.tf`'s MCP service). The worker maps the PagerDuty incident fields onto the agent's existing envelope (`query`, `incident.title`=PD title, `incident.service`=PD service summary, `incident.severity`=PD urgency, `session_id`/`source_event_id`=PD incident id, `source_type`="pagerduty_webhook"), calls `reasoningEngines.query` directly (bypassing the gateway, since the gateway is egress-only), gets back `rca_report`/`executive_summary`/`confidence_band`, and calls PagerDuty's `POST /incidents/{id}/notes` with the RCA text.
4. Grant the worker's own dedicated service account query access to ONLY this one reasoning engine — not project-wide — using `google_vertex_ai_reasoning_engine_iam_member` (role `roles/aiplatform.user`, which the live Google Cloud IAM docs confirm includes the `aiplatform.reasoningEngines.query` permission). This Terraform resource type is confirmed present (via `strings` on the exact `terraform-provider-google-beta_v7.39.0_x5` binary already vendored in `iac/agent/.terraform/`) so no new provider version is needed.
5. This is the one genuinely open product decision this design can't resolve for you: PagerDuty incidents don't inherently carry k8s `cluster`/`namespace`/`pod`. Recommend populating PagerDuty custom fields on the incident (or a static PD-service-id -> cluster/namespace lookup, mirroring the existing `clusters.json` in the cluster-config bucket) and have the worker read that — flagged below as unverified against your live PD account's actual field names.

### Key decisions

- Authenticity control for the public receiver: HMAC X-PagerDuty-Signature verification (PagerDuty's own recommended default, works cleanly on stock Cloud Run) instead of PagerDuty's mutual-TLS option (would need an external HTTPS Load Balancer with a Certificate Manager trust config to terminate/verify client certs — heavier, not needed for v1) or OAuth-bearer webhook auth (requires registering/rotating an OAuth client on the PD side for no real benefit here).
- Two decoupled Cloud Run services (receiver + worker) joined by Pub/Sub, NOT one service that ACKs then keeps working in the background — because Cloud Run throttles CPU after the HTTP response is sent unless 'CPU always allocated' is paid for; a genuinely separate push-triggered request is the only fully reliable way to do the ~60s+ investigation after acking PagerDuty within 5s.
- PagerDuty incident -> {cluster, namespace, pod} resolution: recommend PagerDuty custom fields on the incident (populated by whatever alerting rule created it) as the source of truth, read by the worker, falling back to a static PD-service-id -> cluster/namespace table (same shape as the existing clusters.json in the cluster-config bucket) if custom fields aren't set up. This is a genuine open question for the user/team, not something to silently assume.
- Manage the PagerDuty-side webhook subscription in Terraform (PagerDuty/pagerduty provider, pagerduty_webhook_subscription resource) rather than manual console setup, matching this repo's IaC-first rule — but this introduces a NEW sensitive credential (a PagerDuty API token with webhook_subscriptions.write) that has to be added to whichever pipeline runs `terraform apply` (a new GitHub Actions secret, separate from the existing GCP WIF setup), not just GCP IAM.
- Idempotency against PagerDuty's at-least-once webhook delivery: a lightweight GCS conditional-create marker (touch an empty object keyed by the X-Webhook-Id header, `ifGenerationMatch=0`) in the receiver, reusing existing bucket infra, rather than standing up Firestore just for this.
- RCA note content: post the full `rca_report` (formatted text report `_build_rca_report()` already produces) as the PagerDuty note content, not just `executive_summary` — PagerDuty notes allow up to 65,535 characters (verified from PagerDuty's own OpenAPI schema description) and this repo's typical RCA reports are well under that; keep executive_summary as a fallback only if content ever needs truncating.
- Scope of the PagerDuty write-back for v1: post a note only (per the literal ask). Do not also PATCH incident priority/responders/acknowledge in this pass — that's a natural v2 extension gated on confidence_band, but adding it now increases the PD REST scope (incidents.write already covers notes; priority/responder changes would need additional scopes/roles on the PD token) without being asked for.

### Best practices & references

- PagerDuty V3 webhook signature verification: X-PagerDuty-Signature header contains one or more comma-separated 'v1=<hex>' values (multiple = secret rotation window); compute HMAC-SHA256 of the RAW, unaltered request body using the webhook subscription's per-delivery secret, hex-encode, constant-time-compare against each v1 value. Verifying with a body that any framework/middleware has re-parsed or re-serialized WILL fail — must capture raw bytes before any JSON parsing. ([source](https://github.com/PagerDuty/developer-docs/blob/main/docs/webhooks/04-Signatures.md))
- PagerDuty webhook delivery behavior: 2xx required within 5 seconds for generic/V3 webhooks or PagerDuty treats it as a timeout and retries; retries continue up to 48 hours; delivery is at-least-once (dedupe on the X-Webhook-Id header); PagerDuty's own recommended pattern is to return 202 Accepted immediately and process asynchronously. ([source](https://github.com/PagerDuty/developer-docs/blob/main/docs/webhooks/02-Behavior.md))
- V3 webhook subscription payload shape: {event:{id, event_type, resource_type, occurred_at, agent, client, data}}; for incident.triggered, event.data.type=='incident' with fields id/title/service/urgency/status/incident_key/html_url etc. Subscriptions are created via POST /webhook_subscriptions with events[], filter{type: service_reference|team_reference|account_reference}, delivery_method{url, custom_headers}. ([source](https://github.com/PagerDuty/developer-docs/blob/main/docs/webhooks/01-Overview.md))
- Official Terraform resource for managing the subscription declaratively: pagerduty_webhook_subscription (PagerDuty/pagerduty provider). Confirms `delivery_method.secret` ('the secret used to sign webhook payloads') is only returned on the initial create response — capture it in the same apply and push it straight into Secret Manager rather than storing/copy-pasting it by hand. ([source](https://registry.terraform.io/providers/PagerDuty/pagerduty/latest/docs/resources/webhook_subscription))
- PagerDuty REST API note creation: POST /incidents/{id}/notes, body {"note":{"content": "..."}}, requires incidents.write scope, and REQUIRES a `From` header set to the email of a valid PagerDuty user (even when authenticating with an account-level API token) — a service/bot user must exist in the PD account for this header, or the call fails. ([source](https://developer.pagerduty.com/api-reference/9529ec706026d-create-a-note-on-an-incident))
- PagerDuty REST API authentication: Authorization: Token token=<key> header (account or user API token); all REST calls must be HTTPS. ([source](https://github.com/PagerDuty/developer-docs/blob/main/docs/REST-API/02-Authentication.md))
- Events API v2 (POST https://events.pagerduty.com/v2/enqueue, routing_key + event_action=trigger/acknowledge/resolve) is the mechanism for CREATING PagerDuty incidents from external monitoring — not needed for this task (PagerDuty is the trigger source here, not the destination), but relevant if a later iteration wants the agent to open/resolve its own PagerDuty incidents. ([source](https://github.com/PagerDuty/developer-docs/blob/main/docs/events-API-v2/02-Trigger-Events.md))
- PagerDuty webhook IP safelist (US and EU service regions) for an optional defense-in-depth network allowlist layered on top of (never instead of) signature verification — PagerDuty stopped updating the old dynamic /webhook_ips endpoint in 2022; this static docs page is the current source. ([source](https://github.com/PagerDuty/developer-docs/blob/main/docs/webhooks/11-Webhook-IPs.md))
- aiplatform.reasoningEngines.query is included in the predefined roles/aiplatform.user (also roles/aiplatform.expressUser and roles/aiplatform.admin) per Google Cloud's live Agent Platform IAM roles/permissions page — grant this role to the worker's dedicated SA, scoped to the single reasoning engine resource rather than the whole project. ([source](https://docs.cloud.google.com/gemini-enterprise-agent-platform/machine-learning/general/access-control))
- Resource-level IAM for a single reasoning engine is supported by Terraform today: google_vertex_ai_reasoning_engine_iam_member / _iam_binding / _iam_policy exist in the exact google-beta 7.39.0 provider already vendored in this repo (iac/agent/.terraform/providers/.../terraform-provider-google-beta_v7.39.0_x5) — verified directly via `strings` on that binary in this session (the provider's rendered docs page did not load in this session's browser, so this was confirmed from the binary itself rather than the docs site).
- Cloud Run v2 `ingress` enum includes INGRESS_TRAFFIC_ALL, _INTERNAL_ONLY, _INTERNAL_LOAD_BALANCER, _UNSPECIFIED — confirmed via the same provider binary (this repo's cloudrun_mcp.tf already uses INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER for the internal MCP service; the new public receiver needs INGRESS_TRAFFIC_ALL).

### Risks & gotchas

- Cloud Run silently throttles CPU to near-zero after the HTTP response is flushed (unless 'CPU always allocated' is enabled, which costs more) — a single-service 'ack fast then keep working' design will intermittently fail to finish the investigation. This is why the design uses two Cloud Run services joined by Pub/Sub, not background work in the receiver.
- PagerDuty requires a 2xx within 5 seconds for generic/V3 webhooks; this agent's own measured investigation time is 56-62s (this repo's TROUBLESHOOTING_LOG.md) and can run longer via loop_controller retries — never call reasoningEngines.query from the receiver's request path.
- PagerDuty webhook delivery is at-least-once; without the dedup marker, a retried delivery (e.g. after a receiver cold-start timeout) would trigger a second full paid investigation for the same incident.
- The exact wire shape of PagerDuty custom fields on an `incident.triggered` webhook payload (needed to resolve cluster/namespace/pod) was NOT verified against a live PagerDuty account in this session — confirm the real field names/structure before hardcoding the worker's parser.
- google_vertex_ai_reasoning_engine_iam_member/_iam_binding/_iam_policy were confirmed to exist in the exact provider binary pinned in this repo (via `strings`), but their exact HCL argument names/shape were not read from a fully rendered docs page in this session (developer.pagerduty.com and the Terraform Registry both returned nav-only/empty content to this session's fetch tools). Run `terraform providers schema -json` locally (or check the Registry page directly in a normal browser) to get the exact argument names before writing the HCL.
- Publicly invokable Cloud Run (allUsers run.invoker) can be blocked outright by an org policy constraint (iam.allowedPolicyMemberDomains) if one is set on the GCP project/org — check before assuming this design applies unmodified.
- Managing the PagerDuty webhook subscription via Terraform introduces a new sensitive credential (a PagerDuty API token with webhook_subscriptions.write) that must be supplied to whatever runs `terraform apply` — this is a new secret to provision in CI, distinct from the existing GCP WIF deployer identity, and needs the same 'never commit, never log' handling as any other credential per this project's security rules.
- The REST 'create a note' call requires a `From` header naming a real, active PagerDuty user's email — if that user is ever deactivated/removed, note creation starts failing with 400s; treat this like any other service-account-style credential that needs an owner and a renewal/offboarding process.
- Item 3 in this review (deduplicated root-cause text across executive_summary / RCA section 1 / RCA section 2) is cosmetic but will make its way verbatim into the PagerDuty note; fixing item 3 first (or at least before this ships to real on-call engineers) makes the posted note noticeably cleaner, though it is not a hard technical dependency.

## 9. (Item #9) Repeatable pattern for onboarding new MCP servers (Grafana, Prometheus, Elasticsearch, Confluence, GitHub, ...)

**Effort estimate:** Medium. The module extraction + Pattern A/B split + first server end-to-end (recommend Grafana, since it is Pattern B and directly reuses/proves the extracted module) is roughly 1-2 days including the ADR and the new `secret_token` auth mode in `agent/mcp_client.py`. Each additional server after that is a few hours — one small Terraform file (module instantiation or registration-only block) plus one `MCP_REGISTRY` entry — since the module, Secret Manager wiring, and auth-mode groundwork are reused, not rebuilt per vendor.

### Current state

Today there is exactly ONE self-hosted MCP pattern in the repo, and it is hardcoded, not a reusable module: `iac/agent/cloudrun_mcp.tf` is a flat set of resources (Artifact Registry repo, a dedicated least-privilege runtime SA `sre-k8s-mcp-runtime`, and one `google_cloud_run_v2_service`), gated by `var.enable_custom_mcp`, granted only `roles/container.viewer` cross-project in Project B. The primary tool source, GKE Remote MCP, needs no hosting (fixed Google-managed URL `https://container.googleapis.com/mcp/read-only`, `iac/agent/main.tf` line 30).

Registration into the Agent Registry is 100% imperative today: `scripts/register_endpoints.py` shells out to `gcloud alpha agent-registry services create ...` for a large static list of Google API hostnames (`scripts/googleapis.txt`). `AUDIT_REPORT.md` explicitly flags this as a gap: "Agent Registry endpoint registrations have zero Terraform representation — pure imperative gcloud calls with no state tracking or drift detection."

IAM is already registry-scoped, not per-endpoint: `iac/agent/iap_egressor.tf` grants `roles/iap.egressor` ONCE to the agent's Agent Identity via `google_iap_agent_registry_iam_member`, covering egress to ANY endpoint later registered in the Agent Registry — so today, adding a new registered destination requires no new IAM grant on the egress side. `roles/agentregistry.viewer` (registry-wide, for MCP-server discovery) is granted in `iac/agent/iam.tf`.

Application-level source/tool registration lives in `agent/mcp_client.py` (`MCP_REGISTRY` dict: url/auth/tools/description per source, only two auth modes exist today — `access_token` and `identity_token`) and `agent/nodes/mcp_router.py` (deterministic Phase-1 source pick: `gke`→`gke_remote_mcp`, else→`k8s_mcp`; Phase-2 LLM tool pick constrained by a hard `ALLOWED_TOOLS` frozenset).

No Secret Manager usage exists anywhere in the repo (`grep` found zero hits), and `secretmanager.googleapis.com` is absent from `iac/agent/apis.tf`'s `core_apis` list — a real gap for any server needing a stored credential.

Provider pin: `google`/`google-beta` both `>= 7.0.0, < 8.0.0`; the resolved version in `iac/agent/.terraform.lock.hcl` is exactly `7.39.0`.

### Recommended approach

Verified via the provider's own source: `google_agent_registry_service` is a GA Terraform resource, added to the STABLE `google` provider in v7.39.0 (confirmed in `hashicorp/terraform-provider-google`'s `.changelog/18006.txt`: "Added the `google_agent_registry_service` resource to GA") — and 7.39.0 is the exact version already locked in this repo. This closes the AUDIT_REPORT.md gap with zero provider bump. Stop growing the imperative script for anything beyond its existing bulk Google-API job; register every NEW MCP server declaratively, one `google_agent_registry_service` resource per server — matching ADR-001/ADR-002's own precedent of "Terraform for everything Terraform can express, an imperative script only for what it genuinely can't."

Two repeatable shapes, chosen by where the server actually runs, verified per-vendor (not assumed):
- Pattern A — vendor-hosted remote MCP, no compute needed: GitHub (`github/github-mcp-server`, official, hosted at `https://api.githubcopilot.com/mcp/`) and Confluence/Atlassian (`atlassian/atlassian-mcp-server`, official, GA Feb 2026, hosted at `https://mcp.atlassian.com/v1/mcp`, OAuth 2.1 or API token) both ship official SaaS-hosted endpoints today. Onboarding = one `google_agent_registry_service` + one Secret Manager secret for the credential + a scoped `secretAccessor` grant. No image, no Cloud Run.
- Pattern B — self-hosted MCP on Cloud Run, same shape as today's `cloudrun_mcp.tf`: Grafana (`grafana/mcp-grafana`, official, Grafana Labs org, stdio/SSE/streamable-http, Docker-ready) and Prometheus (`prometheus/prometheus-mcp`, confirmed to be under the real `prometheus` GitHub org, stdio + streamable-HTTP) both ship official self-run servers. Elasticsearch is the one genuine trap: its official `elastic/mcp-server-elasticsearch` states in its own README "This MCP server is deprecated and will only receive critical security updates going forward," superseded by an Elastic Agent Builder MCP endpoint built into Elasticsearch 9.2+/Serverless (effectively Pattern A if you're on 9.2+) — or, for older/self-managed clusters, the actively-maintained community fork `cr7258/elasticsearch-mcp-server` (covers Elasticsearch + OpenSearch) via Pattern B. Do not template the deprecated official image as the default.

Extract today's one hardcoded Cloud Run block into a reusable Terraform module (`iac/agent/modules/mcp_server/`) before a second self-hosted server is added, so Pattern B becomes "one module instantiation + one registry resource" per server, not a copy-pasted file. Because `iap.egressor` is already registry-wide, no new egress IAM is needed per onboarding by default — the genuinely new IAM surface each time is (a) the Cloud Run runtime SA's least-privilege grant on the target system (Pattern B only, mirrors `cloudrun_mcp.tf`'s existing single `container.viewer` grant) and (b) a `secretAccessor` grant scoped to that one server's secret. Optionally tighten later with the newly-verified `google_iap_agent_registry_mcp_server_iam_member`/`_iam_binding` resources, which scope `roles/iap.egressor` to one specific `mcp_server_id` instead of the whole registry — worth adopting once the registry mixes Google APIs with third-party SaaS destinations of different trust levels.

### Key decisions

- Use `google_agent_registry_service` (Terraform, GA, no provider bump) as the only mechanism for registering NEW MCP servers going forward; leave `scripts/register_endpoints.py` untouched for its existing bulk Google-API-hostname job — do not attempt to migrate the whole googleapis.txt list, that is a separate, unrelated cleanup.
- Two onboarding shapes selected by hosting model, not one universal template: Pattern A (vendor remote MCP — registration + secret only) vs Pattern B (self-hosted Cloud Run MCP — module + registration + secret + target-system IAM).
- Extract `cloudrun_mcp.tf`'s single hardcoded Cloud Run service into a reusable module (`iac/agent/modules/mcp_server/`) before onboarding a second self-hosted server, so the existing working service becomes the proof of the template rather than a one-off.
- Add `secretmanager.googleapis.com` to `iac/agent/apis.tf` and adopt Secret Manager — one secret per server, resource-level `secretAccessor` grant — as the only credential-storage mechanism; never bake tokens into Cloud Run env vars or code.
- Extend `agent/mcp_client.py`'s `MCP_REGISTRY` auth model from today's two modes (`access_token`, `identity_token`) to a third (`secret_token` or similar) for SaaS servers needing a static Bearer/PAT from Secret Manager — land this once, generically, before the first Pattern-A server, not per-vendor.
- For Elasticsearch specifically: decide per-cluster whether to require 9.2+ and use Elastic's built-in Agent Builder MCP endpoint (Pattern A) instead of the vendor's deprecated separate server, or use the community fork (Pattern B) for older/self-managed clusters — record the choice in the ADR, analogous to ADR-001's 'existing infra, different owning team' framing.
- Decide whether to keep the current registry-wide `iap.egressor` grant (simpler, fine while the registry only holds Google APIs + one internal Cloud Run service) or move to per-server scoped grants via `google_iap_agent_registry_mcp_server_iam_member` once third-party SaaS destinations (GitHub, Atlassian) start populating the same registry — do this migration once, for all servers, not incrementally.

- Grafana: official OSS MCP server maintained by Grafana Labs (github.com/grafana/mcp-grafana), supports stdio/SSE/streamable-http transports, Docker deployment, auth via GRAFANA_SERVICE_ACCOUNT_TOKEN (GRAFANA_API_KEY is deprecated). ([source](https://github.com/grafana/mcp-grafana))

## 10. (Item #5) On-prem Kubernetes cluster investigation via GKE Fleet Connect Gateway

**Effort estimate:** Medium-large. Scope: one new Terraform module (fleet membership + IAM), one new imperative bootstrap script (Connect Agent install + RBAC generation — cannot be pure Terraform), a code change to mcp/server.py's cluster-auth branch, a schema change to clusters.json/mcp_client.py's registry, and two docs updates (least-privilege-iam.md, new ADR). Real end-to-end validation requires an actual reachable on-prem-style cluster (not GKE Autopilot), which is the main driver of the higher-than-'medium' estimate — this can't be fully proven with the infrastructure already in this repo.

### Current state

Verified in repo: the agent has exactly two cluster-access paths today, both GKE-only. (1) Primary — GKE Remote MCP, Google-managed, hardcoded to `https://container.googleapis.com/mcp/read-only` (agent/mcp_client.py:5,100), every call requires `parent = projects/{project}/locations/{region}/clusters/{cluster}` (agent/mcp_client.py:186-188). I fetched Google's own docs for this endpoint (docs.cloud.google.com/kubernetes-engine/docs/reference/mcp and .../how-to/use-gke-mcp) and neither mentions Connect Gateway, fleets, or non-GKE clusters anywhere — this MCP source is GKE-cluster-scoped only, confirmed not assumed. (2) Fallback — a custom Cloud Run MCP (mcp/server.py) the agent calls with an identity token; its get_k8s_clients() talks to the cluster's raw Kubernetes API using GKE_CLUSTER_ENDPOINT + a CA cert pulled from GCS + a Google OAuth2 access token used directly as the K8s Bearer token (mcp/server.py:34-79). That bearer-token pattern only authenticates because GKE's control plane has built-in Cloud IAM integration — a vanilla on-prem API server will not accept a GCP access token as auth. Interesting existing fact: the routing layer already has an 'onprem' concept — agent/prompts.py:54 and agent/nodes/mcp_router.py:82-88 already route non-'gke' cluster_type to k8s_mcp as primary, and the clusters.json schema comment in agent/mcp_client.py:126 already lists type: gke | custom. But nothing downstream of that routing decision can actually reach a real on-prem cluster — mcp/server.py only knows GKE-style-endpoint+GCS-CA-cert or local kubeconfig (dev only). So 'onprem' today is a routing label with no working transport behind it. Cross-project IAM (iac/gke-access/crossproject_iam.tf) grants the agent's AGENT_IDENTITY principalSet (principalSet://agents.global.org-{org_id}.system.id.goog/attribute.platformContainer/aiplatform/projects/{number}, defined in iac/agent/main.tf:24) four project-level roles in Project B: container.viewer, mcp.toolUser, logging.viewer, monitoring.viewer — a pure Cloud-IAM model with zero Kubernetes RBAC anywhere in the repo, because GKE never needed it. No fleet APIs (gkehub.googleapis.com, gkeconnect.googleapis.com, connectgateway.googleapis.com) appear anywhere in iac/gke-access/gke.tf or iac/agent/apis.tf; no google_gke_hub_membership resource, no Connect Agent, no RBAC manifests exist in the repo.

### Recommended approach

Confirmed current terminology (Google's docs, fetched July 2026): the product is 'Fleet management' with a component called the 'Connect gateway', backed by an in-cluster 'Connect Agent'; the underlying API/IAM-role prefix is still gkehub.* (legacy 'GKE Hub'/'Anthos' branding persists at the API-surface level even though the product name changed). Do not try to extend GKE Remote MCP to on-prem — verified it has no fleet/Connect Gateway support. Instead, route on-prem exclusively through the existing custom Cloud Run MCP (k8s_mcp), reworked to reach the cluster through Connect Gateway's REST endpoint (https://connectgateway.googleapis.com/v1/projects/{project_number}/locations/{location}/gkeMemberships/{membership}) instead of a direct GKE_CLUSTER_ENDPOINT. Keep authenticating with the SAME already-existing dedicated mcp_runtime service account (iac/agent/cloudrun_mcp.tf) rather than trying to push the AGENT_IDENTITY SPIFFE principalSet into Kubernetes RBAC — Google's documented RBAC-generation flow for Connect Gateway (generate-gateway-rbac --users=) and its third-party-identity docs are built around plain user/SA emails or Workforce Identity Federation principals (a different WIF pool family than Agent Identity's agents.global.org-*.system.id.goog pool), so reusing the existing SA is the verified-supported path, not a guess. This adds a genuinely new authorization layer this repo has never needed: Kubernetes RBAC inside the on-prem cluster, on top of Cloud IAM — because unlike GKE, an on-prem API server has no native Cloud IAM trust.

### Key decisions

- Which project hosts the fleet membership — reuse Project B (sreagent-demo) to preserve the existing two-project topology from ADR-001, rather than introducing a third project.
- Which identity authenticates through Connect Gateway — reuse the existing dedicated mcp_runtime Cloud Run service account (already read-only, already least-privilege per docs/least-privilege-iam.md section 5) rather than extending the AGENT_IDENTITY principal into Kubernetes RBAC, which is an unverified/unsupported combination.
- Where the new IaC lives — a new module (iac/onprem-fleet/ or similar), not folded into iac/gke-access/, because ADR-001 explicitly scopes that stack to 'a GCP-project-owned GKE cluster + project-level cross-project IAM'; fleet membership + in-cluster RBAC is a different resource shape and trust boundary.
- How the Connect Agent gets installed — accept that this one step is not cleanly Terraform-native (it requires gcloud container fleet memberships register run with real kubectl access to the on-prem cluster), and document it as a one-time imperative bootstrap script, mirroring the repo's existing precedent (scripts/attach_gateway_to_engine.sh — 'the one step Terraform cannot yet express').
- How clusters.json / the cluster registry models on-prem clusters — needs a distinct cluster_type (e.g. onprem) carrying fleet membership name + project number + location, replacing today's ambiguous custom catch-all so mcp/server.py knows to use the Connect Gateway auth branch instead of the direct-endpoint branch.

### Best practices & references

- Connect gateway supports GKE, other-cloud, and on-premises clusters uniformly, but the request-authorization path genuinely differs by cluster type: for GKE, the gateway connects to the cluster directly; for non-GKE clusters the request is forwarded through the Connect service and Connect Agent to the cluster's own API server, which then authorizes it — meaning the on-prem cluster's own RBAC is the real gatekeeper, not just Cloud IAM. ([source](https://docs.cloud.google.com/kubernetes-engine/enterprise/multicluster-management/gateway))
- The Connect Agent is an in-cluster Deployment that opens a long-lived, encrypted outbound connection to Google — it is only required for clusters outside Google Cloud; GKE clusters never need it. It needs outbound HTTPS reachability to googleapis.com and gkeconnect.googleapis.com, and typical resource use is ~500m CPU / 200Mi memory. ([source](https://docs.cloud.google.com/kubernetes-engine/fleet-management/docs/connect-agent))
- Setup requires enabling connectgateway.googleapis.com, gkeconnect.googleapis.com, gkehub.googleapis.com, cloudresourcemanager.googleapis.com; granting roles/gkehub.gatewayReader (read-only) or gatewayEditor/gatewayAdmin, plus roles/gkehub.viewer to fetch kubeconfigs; and separately configuring in-cluster RBAC (impersonation ClusterRole/ClusterRoleBinding), which gcloud container fleet memberships generate-gateway-rbac ... --apply can generate and apply automatically instead of hand-writing YAML. ([source](https://docs.cloud.google.com/kubernetes-engine/enterprise/multicluster-management/gateway/setup))
- Only roles/gkehub.gatewayAdmin includes the gkehub.gateway.stream permission needed for exec/attach/cp/port-forward — a read-only investigation agent should be granted roles/gkehub.gatewayReader only. Service accounts are explicitly supported for automated/programmatic access via impersonation (gcloud config set auth/impersonate_service_account), which is the documented pattern for an unattended agent like this one. ([source](https://docs.cloud.google.com/kubernetes-engine/enterprise/multicluster-management/gateway/using))
- GKE clusters on Google Cloud must be registered to a fleet explicitly and get roles/container.admin for cluster-admin-equivalent access; clusters outside Google Cloud instead require explicit Kubernetes RBAC cluster-admin (or narrower) role assignment via kubectl/generate-gateway-rbac — confirming IAM alone is not sufficient authorization for the on-prem case, unlike this repo's current GKE-only model. ([source](https://docs.cloud.google.com/kubernetes-engine/fleet-management/docs/before-you-begin))
- Third-party/federated identities bind to on-prem cluster RBAC using principal strings scoped to Workforce Identity Federation workforce pools (principal://iam.googleapis.com/locations/global/workforcePools/[POOL_ID]/subject/[SUBJECT]) — a distinctly different WIF pool family from Vertex AI Agent Engine's AGENT_IDENTITY pool (agents.global.org-{org_id}.system.id.goog), which is why this plan avoids binding Kubernetes RBAC directly to the agent's own identity and instead reuses a plain service account. ([source](https://docs.cloud.google.com/kubernetes-engine/enterprise/multicluster-management/gateway/setup-third-party))
- The GKE remote MCP server (container.googleapis.com/mcp) reference and how-to docs describe it exclusively in terms of GKE clusters and node pools, with zero mention of Connect Gateway, fleets, or non-GKE/on-prem clusters — confirms this repo's primary MCP source cannot be extended to on-prem and the custom Cloud Run MCP fallback is the only viable integration point. ([source](https://docs.cloud.google.com/kubernetes-engine/docs/reference/mcp))
- Terraform's Google provider has a google_gke_hub_membership resource for registering a cluster's fleet membership object (via endpoint.gke_cluster.resource_link for GKE clusters), so at least the membership record itself can be IaC-managed even though Connect Agent installation into a non-GKE cluster is a separate, non-Terraform-native step. ([source](https://registry.terraform.io/providers/hashicorp/google/latest/docs/resources/gke_hub_membership))
- Current CLI surface (verified, not the deprecated 'container hub' branding) is gcloud container fleet memberships register / get-credentials / generate-gateway-rbac; the older gcloud container hub memberships register form still resolves but reflects the pre-'Fleet' rebrand naming — use the fleet form going forward. ([source](https://cloud.google.com/sdk/gcloud/reference/container/fleet/memberships/register))

## 11. (Item #11) Migrate LangGraph agent to Google ADK 2.0 (in testing-adk-agent clone)

**Effort estimate:** Large -- this is a full framework rewrite of the agent's reasoning core (5 LLM nodes + the loop/state model) plus a new MCP-wiring layer, run against a live GCP two-project topology with a gateway that took multiple days to debug once already (see FINAL_RCA.md / TROUBLESHOOTING_LOG.md in testing2). Realistic scope: 1 dedicated multi-week workstream, not something to interleave with the other 10 items. Recommend it get its own session/sprint, gated behind a 1-2 day spike (Phase 0 below) before committing calendar time, because the single biggest unknown -- ADK 2.0's actual graph-workflow API for a confidence-band exit loop -- could not be confirmed from public docs in this research pass.

### Current state

FACT (read directly): testing2-gcp-sre-agent/agent/ is a 9-node LangGraph StateGraph (agent/graph.py): input_normalizer -> context_resolver -> task_planner -> mcp_router -> tool_executor -> [conditional: evidence_extractor or skip] -> task_evaluator -> loop_controller -> [conditional: loop back to task_planner, or finish] -> rca_builder -> END. AgentState (agent/state.py) is a TypedDict with Annotated reducers: operator.or_ for dict-merge fields (resolved_context, investigation), a custom _append for list fields (evidence_ids, tool_history, errors, sources_skipped, evaluation_ids). Five of the nine nodes are LLM calls via agent/gemini_client.py's llm()/llm_json() (direct google-genai Vertex client, temperature=0, thinking_budget=0, manual JSON-repair parsing) driven by prompts in agent/prompts.py: input_normalizer, task_planner, mcp_router (phase 2 tool selection), evidence_extractor, task_evaluator, rca_builder. context_resolver and loop_controller are pure deterministic Python (no LLM). mcp_router's phase-2 pattern is deliberate: the LLM proposes ONE tool name + args as JSON (never calls it directly); tool_executor then validates against an allowlist/forbidden-combo list (agent/mcp_client.py: ALLOWED_TOOLS, BLOCKED_ACTIONS) before executing -- this hand-rolled separation is exactly the user's own cloud.md rule ('Deterministic logic handles detection/validation. AI reasons on top -- AI does not execute'). agent/main.py wraps the compiled graph in a hand-written SREAgent class (set_up()/query() classmethods) that also does Model Armor sanitize (input+output), Vertex AI Memory Bank recall/store, GCS RCA persistence, and structured event_type=sre_agent_run JSON logging around graph.invoke(). Deployment is Terraform-native: iac/agent/agent_engine.tf creates a google_vertex_ai_reasoning_engine with identity_type=AGENT_IDENTITY, source_code_spec.inline_source=filebase64(agent.tar.gz), python_spec{entrypoint_module=agent.main, entrypoint_object=SREAgent, version=3.11, requirements_file=agent/requirements.txt}. An env var already present in Terraform, ADK_ENABLE_MCP_GRACEFUL_ERROR_HANDLING=true, is an ADK-specific setting that is currently a no-op for the LangGraph runtime -- direct evidence the ops team anticipated this migration. Agent Gateway attach (iac/agent/agent_gateway.tf) is a property of the ReasoningEngine resource + a post-apply script (attach_gateway_to_engine.sh), entirely independent of what code runs inside the entrypoint. invoke_agent.py defines exactly 16 SCENARIOS (grep-verified) used for parity testing, each posting a query/cluster/namespace/pod/severity payload and reading back status/confidence_band/tool_calls/evidence_ids/rca_report. testing-adk-agent (~/projects/testing-adk-agent, GitHub AshminPy/testing-adk-agent) was diffed byte-for-byte against testing2-gcp-sre-agent/agent -- zero differences found, confirming it is currently an untouched clone with no ADK-specific code yet.

### Recommended approach

Do not treat this as a rewrite-everything task. Spike first (Phase 0) to close the one real unknown -- ADK 2.0's exact loop/graph-workflow API for a confidence-band-gated investigation loop -- because every later estimate depends on whether that maps to a documented LoopAgent/SequentialAgent composition or requires a custom BaseAgent subclass. Reuse aggressively: prompts.py content, the _build_rca_report/_build_executive_summary formatting functions, the GCS/Memory Bank/Model Armor side-effect code, the two-project Terraform topology, and the inline_source/filebase64 packaging mechanism all carry over with little or no change, because AdkApp (vertexai.agent_engines.AdkApp) is designed to slot into the exact same google_vertex_ai_reasoning_engine Terraform resource this repo already uses -- only entrypoint_object and requirements.txt change at the infra layer. The two things that genuinely change are the state model (ADK's untyped session.state dict vs LangGraph's typed-and-reduced AgentState) and the tool-execution boundary (ADK's native LlmAgent+McpToolset auto-calls tools, whereas the current design deliberately keeps the LLM from calling tools directly) -- both need an explicit decision recorded in a new ADR before code is written, not discovered mid-port. Validate parity using the existing 16 invoke_agent.py scenarios and the existing obs_event structured logging -- no new test harness or instrumentation is needed, just a second run of what already exists pointed at the new deployment.

### Key decisions

- Where does the deterministic tool-execution gate live post-migration: keep the current two-step 'LLM proposes tool+args as JSON, code validates against ALLOWED_TOOLS/BLOCKED_ACTIONS before calling' pattern verbatim (safest, matches existing cloud.md rule, but forgoes ADK's native auto function-calling convenience), versus adopting ADK's LlmAgent+McpToolset native tool-calling with the allowlist check moved into a before_tool_callback (less code, but the model calls the tool directly through the framework and the validation becomes a can-veto-after-the-fact callback rather than a hard gate before the call is even attempted).
- How to represent AgentState in ADK's untyped session.state: one flat JSON-blob key that mirrors today's dict-with-reducer shape (minimal redesign, but re-adds manual merge logic ADK doesn't give you for free) versus decomposing into ADK's native prefix-scoped keys (session/user:/app:/temp:) which is more idiomatic ADK but a bigger redesign of every node's read/write contract.
- Whether to use ADK 2.0's new graph-based workflow runtime (closer conceptual match to LangGraph's StateGraph, but its concrete API was not verifiable from public docs in this session) or fall back to a LoopAgent/SequentialAgent template-workflow composition (documented and stable, but explicitly called 'superseded' as of ADK 2.0) -- this decision should be made only after the Phase 0 spike, not before.
- Whether Model Armor / Memory Bank / GCS-persistence side effects move into ADK plugins (framework-native extension point) or stay as a thin wrapper class around AdkApp similar to today's SREAgent class (lower risk, reuses proven code, but doesn't get any ADK-native benefit from the plugin system).
- Whether the migration targets a net-new reasoning engine + entrypoint inside the SAME sreagent-t2-demo Project A (simpler IAM/network, but risks confusion with the production LangGraph engine) or a fully separate project (cleaner isolation, matches how the mTLS clean-room investigation was already done in this repo's history, but duplicates gateway/IAM setup cost).

### Best practices & references

- Official ADK docs moved: google.github.io/adk-docs now 301-redirects to adk.dev (confirmed live via redirect headers during this research). Bookmark/cite adk.dev going forward, not the old google.github.io path. ([source](https://adk.dev/))
- ADK Python 2.0 GA'd at Google I/O 2026 (May 19, 2026). Current PyPI release is google-adk 2.5.0, released 2026-07-16, requires Python >=3.10 (repo's python_spec.version=3.11 in agent_engine.tf is compatible). ([source](https://pypi.org/project/google-adk/))
- MCP tools in ADK are declared via google.adk.tools.mcp_tool.McpToolset, with StdioConnectionParams (local process) or StreamableHTTPConnectionParams (remote, over HTTP, arbitrary headers for auth) as connection_params. tool_filter narrows which server tools are exposed to the LlmAgent. ([source](https://adk.dev/tools-custom/mcp-tools/))
- adk deploy agent_engine is the documented CLI path for fresh ADK projects (adk deploy agent_engine --project ... --region ... --display_name ... --staging_bucket ... <folder>), but it is NOT the only path: wrapping the agent in vertexai.agent_engines.AdkApp(agent=root_agent) and pointing an existing Terraform google_vertex_ai_reasoning_engine resource's python_spec.entrypoint_object at that module-level AdkApp instance is an independently documented, IaC-native alternative that reuses the exact inline_source/filebase64 packaging this repo already uses. ([source](https://docs.cloud.google.com/python/docs/reference/vertexai/latest/vertexai.agent_engines.AdkApp))
- As of ADK 2.0, the older template workflow agents (SequentialAgent/LoopAgent/ParallelAgent) are documented as 'superseded by more flexible workflow structures, including graph-based workflows and dynamic workflows' for Python/Go -- but adk.dev's public docs did not yield concrete graph-workflow node/edge API syntax in this session. Treat the exact graph-workflow API as UNVERIFIED and spike it hands-on before committing the port design. ([source](https://adk.dev/2.0/))
- ADK session.state is a loosely-typed dict with prefix scoping (no prefix=session, user:, app:, temp:) updated via event state_delta -- there is no TypedDict-with-reducer equivalent to LangGraph's operator.or_/list-append annotated state. Any port of AgentState must be redesigned around this weaker-typing model or wrapped in a single JSON-blob state key. ([source](https://adk.dev/sessions/state/))
- Google's 2026 platform rebrand (Vertex AI -> Gemini Enterprise Agent Platform, 'Agent Engine' UI-relabeled toward 'Deployments'/'Agent Runtime') does NOT change the underlying Terraform/API resource type -- it remains ReasoningEngine / google_vertex_ai_reasoning_engine for backward compatibility. This rebrand is orthogonal to the LangGraph->ADK decision and already partly reflected in this repo's own comments (main.py docstring already says 'Gemini Enterprise Agent Runtime entrypoint'). ([source](https://cloud.google.com/agent-builder/agent-engine/overview))

### Risks & gotchas

- ADK 2.0's graph-based workflow runtime -- the most natural analog to the current LangGraph StateGraph -- has thin public documentation as of this research (adk.dev pages returned only high-level marketing-style descriptions, no node/edge class names or method signatures); do not commit to a design assuming specific API shapes without opening the installed google-adk 2.5.0 source or its API reference directly.
- ADK's session.state has no typed-reducer equivalent to LangGraph's Annotated[Dict, operator.or_] / Annotated[List, _append] -- a naive port that just dumps AgentState fields into session.state keys will silently lose the current merge/append semantics (e.g. investigation dict fields overwriting each other instead of merging, evidence_ids overwriting instead of appending) unless every write path is redesigned around ADK's state_delta/event model.
- Gateway attach is currently fragile and has already caused a multi-day production incident in this exact repo (see FINAL_RCA.md / TROUBLESHOOTING_LOG.md, 2026-07-16/17 mTLS + accumulated engine-side state root cause) -- deploying a second, ADK-based reasoning engine behind the same or a new Agent Gateway should be treated as a repeat of that risk surface, not a solved problem, even though the gateway-attach mechanism itself should be framework-agnostic.
- ADK_ENABLE_MCP_GRACEFUL_ERROR_HANDLING is already set in Terraform but is currently inert (LangGraph doesn't read it) -- once the entrypoint becomes ADK-based this env var starts actually doing something; verify its documented behavior (graceful vs current fail-fast handling of gateway-denied 403 MCP calls) before assuming it's a no-op change.
- Model Armor's app-level sanitize path is currently gated off when the gateway is enabled (agent_env local: var.enable_agent_gateway ? {} : {MODEL_ARMOR_TEMPLATE=...}) specifically to avoid a redundant double-inspection -- if the ADK port re-adds app-level sanitization unconditionally (e.g. via a plugin applied regardless of gateway state) it would silently reintroduce the redundant-inspection problem this repo deliberately avoided.
- google-adk 2.5.0 requires Python >=3.10; the repo's python_spec.version=3.11 is compatible today, but pin the exact google-adk version in requirements.txt (do not float it) given how fast-moving this package is (2.0 GA'd May 2026, already at 2.5.0 by July 2026).
- Do not use the `adk deploy agent_engine` CLI as the deployment mechanism -- it creates a new reasoning engine directly from the CLI, bypassing this repo's two-project Terraform IaC entirely, which conflicts with the user's own 'IaC before manual: if it can be Terraformed, it must be' rule (cloud.md) and would create a resource with no Terraform state tracking it.
