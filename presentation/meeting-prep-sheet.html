liveness-fail-pod

node-selector-pod

FAQ — short, direct answers

What do we have in the golden dataset today?

35 test cases total — 14 from an earlier testing environment, 21 built this week for the current cluster. Today's demo runs the 10 that are fully validated end to end.

How did we create the golden dataset?

Each case pairs one deliberately-broken Kubernetes resource with a written-down correct answer — the real root cause, the keywords that should appear, and a minimum confidence bar. We deploy the real broken resource, ask the agent to investigate, and score its real answer against what we wrote down.

How are we measuring, and what are we measuring?

Root-cause accuracy (did it name the real cause), confidence calibration (was it honestly confident, not just fluent), cost, and latency — all from real runs, not estimates. One known gap: the deployed agent's response doesn't expose which tools it called, so we can't yet score "did it investigate the right way" in this mode — only "did it conclude the right thing."

What is confidence score and how does the loop exit work?

Every answer gets a 0–1 confidence score and a band: auto (high, ~0.85+), review (medium), or escalate (low — hand to a human). The investigation loop stops either when confidence is high enough, or after a hard iteration cap so it can never run away indefinitely.

What security layers and controls do we have today?

Model Armor filters input and output. IAM is least-privilege, no broad roles. Identity uses Workload Identity — no static keys anywhere. Every tool the agent has is read-only, it can't write or execute on the cluster. All traffic routes through an IAP-gated Agent Gateway. A human always approves before anything actually changes.

What does reliability look like today?

The loop has a hard exit condition, so it can't run forever. When evidence conflicts or is missing, it escalates instead of guessing — we've seen this happen for real in testing. Every run is logged and traced. One real, specific gap found through testing: a permissions issue reading pod logs in one namespace — already root-caused, not yet fixed.

Is this in production?

No — this is a validated pilot on a live GKE cluster, not customer-facing production traffic. Recommended next step is a controlled pilot before wider rollout.

What does it cost to run?

About a quarter of a cent per investigation, ~20 seconds average. At 1,000 investigations a month that's roughly $2.50 — the real cost driver at scale is engineering time, not compute.

What happens if the agent is wrong?

It never takes action itself — it only recommends. A human reviews and approves every remediation. Nothing changes in the cluster without a person deciding to change it.

How does the confidence score actually work?

Two real scoring functions run on every investigation: one scores how complete the evidence is, one scores confidence in the root cause itself. Both feed into a 0-1 number and a band (auto / review / escalate). It's not the model just saying a number — it's a deterministic score built from what evidence was actually collected.

How does the loop exit work?

After each round of evidence gathering, a loop controller checks: is confidence high enough to stop? If yes, it exits and writes the RCA. If not, it goes back for another round — up to a hard iteration cap, so it can never run forever. Every real run logs which of the two happened (confidence_sufficient or max_iterations).

How does SPIFFE work here?

It's how the agent proves who it is without a password or key. Google issues it a short-lived cryptographic identity (Workload Identity) tied to exactly this workload — nothing stored, nothing to leak, and it can't be reused if copied. That identity is what IAM and the Agent Gateway check before allowing any action.

What are the monitoring metrics and how do they help? correction: 12, not 13

12 real metrics, already deployed: invocations, errors, escalations, cost, token usage, confidence band, loop exit reason, tool failures, routing failures, unresolved-cluster cases, evidence-storage failures, and latency. 12 alert policies sit on top of them — so if cost spikes, error rate climbs, or the agent starts escalating too often, someone gets paged automatically, not after a customer notices.

How would we set up an evaluation CI/CD pipeline in future?

Honest answer: this doesn't exist yet — checked, no workflow runs eval automatically today. The real plan: run the golden dataset automatically on every PR to the agent code, block the merge if pass rate drops below a threshold, and store each run's results as a build artifact so we can track accuracy over time, not just at demo time.

How does Model Armor work and what does it actually catch?

It's a Google Cloud service that inspects text going in and coming out of the model — checks for prompt injection attempts, jailbreaks, and sensitive data (PII) before it's acted on or shown. It's wired at the application level today; a gateway-level version is still blocked on a real Google API limitation we found, not something we skipped.

What cost and safety controls do we actually have?

Cost: every run's tokens and dollars are tracked individually, with an alert if spend spikes. Safety: the investigation loop has a hard iteration cap so it can't run away, every tool is read-only so it can't damage anything, and only high-confidence answers ever get marked "auto" — anything less goes to a human.

How are we measuring agent accuracy and correctness specifically?

Two things, kept deliberately separate: did it call the right tools and finish the investigation (process), and did it actually name the right root cause with honest confidence (correctness). A demo that only proves the first one isn't proof the agent works — we score both.

Is the Memory Bank actually wired today? yes, confirmed in code

Yes — checked the real code, not the diagram. Before investigating, it recalls up to 3 past incidents on that same cluster/namespace and includes them as context. After finishing, it writes the new incident back. If memory recall fails for any reason, it degrades gracefully and just proceeds without it — never blocks the investigation.

What LLM actually powers this?

Gemini, via Vertex AI — called through our own provider-neutral adapter layer, not hardcoded to one vendor. If we needed to swap models later, that's a config change, not a rewrite.

What's the kill switch if something goes wrong?

The agent never executes anything itself — every tool is read-only, and every fix requires a human to approve and run it. There's no action for a "kill switch" to stop, by design, because it was never given the ability to act in the first place.
